Three cooperating modules form a tenant lifecycle pipeline:
- `churchTenantProvisioning.ts` is the core entry point: `provisionChurchTenant()` ensures the root Firestore doc exists (with idempotent patching via `buildRootDocPatch`), creates Storage folders for `configuracoes` and `financeiro`, and exposes `migrateAllChurchTenants()` for batch backfills. It explicitly avoids creating "ghost" docs unless `allowCreateRoot` is set.
- `churchTenantFields.ts` provides a thin, Flutter-synced field stamping layer (`tenantFieldsPatch`, `withTenantFieldsStamp`, `needsTenantFieldsStamp`) that mirrors `flutter_app/lib/core/data/church_tenant_fields.dart`, keeping `churchId`/`tenantId` in sync across all church data.
- `churchTenantConsolidation.ts` orchestrates the full consolidation flow: resolves the canonical church ID via `resolveCanonicalChurchDocId`, provisions the tenant, runs cluster data sync through `runSyncChurchClusterDataFromRichest`, and migrates the legacy `members` subcollection to `membros` in batches of 400.

Dependency direction is one-way: consolidation depends on provisioning and canonical resolution; provisioning depends only on Storage helpers and forbidden-test-id filtering. All functions are pure or side-effect scoped, returning typed result objects (`ProvisionChurchTenantResult`, `ChurchTenantConsolidationResult`) rather than throwing, except for argument validation which throws `HttpsError`.
