Three focused files form a small admin tooling layer on top of firebase-admin:
- `adminDb.ts` is a thin bootstrap module that lazily initializes the default Firebase app (guarding against early imports before `index.ts`) and exports lazy accessors for `firestore()` and `storage().bucket()`, centralizing SDK initialization.
- `migrateTenantFirestoreCollections.ts` exposes two callable functions (`migrateTenantFirestoreCollections`, `migrateAllTenantsFirestoreCollections`) that recursively copy documents from legacy collections (`igrejas/{tid}/noticias` → `eventos`, `chat_threads` → `chats`) using batched pagination (BATCH_LIMIT=400) with idempotent merge writes. Per-tenant migration state is tracked in a `_meta/firestore_collection_migration_v1` document with running/completed/error statuses and server timestamps.
- `migrateStorageConsolidated.ts` provides a richer migration pipeline (`runStorageConsolidationMigration`) covering members, avisos, eventos, and patrimonio modules. It uses `sharp` to re-encode images to WebP at full/thumb variants, reads from multiple legacy storage paths plus HTTP sources, and optionally refreshes the members directory cache via `recomputeMembersDirectoryFromDocs`. A master-only callable endpoint wraps this with dry-run support.

Dependency direction: both migration scripts import `firebase-admin` directly (bypassing `adminDb.ts`'s lazy wrapper) and only depend on shared helpers like `membersDirectoryCache`. There is no cross-import between the two migration files; each is independently callable via `functions.https.onCall`.
